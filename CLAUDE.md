**Key architecture decisions:**
- Astro-native throughout — no React/Vue/Svelte. Server-rendered pages, query-param-driven filtering/pagination, Astro Actions (zod-validated) for mutations. No client-side state management.
- Auth: `@supabase/ssr` with PKCE flow (Supabase's SSR default). `/auth/callback` handles the `?code=` exchange for both signup confirmation and password recovery via one shared code path (`next` query param picks the destination).
- Roles: single `user_role` enum on `profiles` (`customer`, `sales_staff`, `inventory_staff`, `admin`, `super_admin`). No separate roles/permissions tables.
- RLS role-check helper `private.current_role()` is `SECURITY DEFINER` + lives in the non-exposed `private` schema specifically to avoid recursion when called from within `profiles`' own policies — deliberate design, don't "simplify" it back to `SECURITY INVOKER`.
- `handle_new_user()` trigger (also `private` schema, hardened `search_path`) auto-provisions `profiles` + `customers` rows on signup.
- `orders`/`order_items` are **still read-only via RLS for every role**, including admin/super_admin — that never changed. Phase 7 didn't add mutation policies; `place_order()`/`update_order_status()` (both `SECURITY DEFINER`) are the only paths that ever write to them, orchestrating order/order_items/payments/inventory changes together with their own explicit authorization checks. Don't add direct mutation policies to these tables — that would create a parallel, uncontrolled write path.
- `inventory_movements` and `audit_logs` are append-only by omission — no UPDATE/DELETE policy exists for any role.
- Middleware (`src/middleware.ts`) gates `/account`, `/checkout`, `/sales` (any authenticated user, `/sales` additionally role-checked to `sales_staff`/`admin`/`super_admin`), and `/inventory`/`/crm`/`/admin` (role-checked, `/admin` to `admin`/`super_admin` only) using boundary-aware prefix matching (`pathname === prefix || pathname.startsWith(prefix + "/")`). `/cart` is deliberately **not** protected — it's a pure `localStorage` read with no DB call.
- Product images: plain `image_url` text field (paste a URL), Supabase Storage deliberately deferred.
- Every product always has a matching `inventory` row: a `provision_product_inventory` trigger (AFTER INSERT on `products`, `SECURITY INVOKER`) auto-creates a zero-quantity row. Deliberately not `SECURITY DEFINER` — the roles allowed to insert products already match the roles allowed to insert inventory, so no privilege elevation is needed.
- `quantity_on_hand` changes through exactly two paths: `record_inventory_movement()` (RPC, `SECURITY INVOKER`, client-callable — restock/adjustment/damaged only) and `private.apply_order_stock_movement()` (Phase 7, internal-only, sale/return only, reachable exclusively from `place_order()`/`update_order_status()`). **`record_inventory_movement()` was deliberately left untouched by Phase 7** — it still unconditionally rejects `'sale'`/`'return'` and any `reference_order_id`, exactly as shipped in Phase 5. Order-driven stock movements were given their own private helper instead of extending the public RPC, specifically so `inventory_staff`/`admin`/`super_admin` (who already have direct RLS grants on `inventory_movements`/`inventory`) can't call a `'sale'` movement against an arbitrary order id — the private helper is unreachable via PostgREST at all. Both paths still enforce non-negative stock via the same `quantity_on_hand >= 0` check constraint.
- Don't reintroduce a direct app-layer insert into `inventory` for new products (e.g. inside `createProduct`) — provisioning is the trigger's job, not the Action's.
- `customer_metrics` (view, `SECURITY INVOKER`) is built `profiles LEFT JOIN orders`, not an aggregation over `orders` alone — every customer gets a row (zero/null metrics included) even with no orders. Visibility rides entirely on existing `profiles` RLS; don't add a separate RLS policy for it.
- `customer_contact_email()` (RPC, `SECURITY DEFINER`) is the only way the app can see a customer's email other than the customer's own session — `auth.users` isn't otherwise exposed. Lives in `public` (unlike `current_role()`/`handle_new_user()`) specifically so it's callable via `supabase-js`. A real anonymous-access bug was found and fixed here mid-Phase-6: Supabase auto-grants `EXECUTE` on new `public` functions to `anon` directly (not just via the `PUBLIC` pseudo-role, so `revoke ... from public` alone doesn't strip it — `anon` must be revoked explicitly too), and `role NOT IN (...)` evaluates to `NULL`, not `TRUE`, when the role itself is `NULL` (an anonymous caller) — the check must explicitly reject a `NULL` role rather than relying on `NOT IN`. Keep both fixes in mind for any future `SECURITY DEFINER` function in `public`.
- Staff CRM notes live in their own `customer_notes` table (one row per customer, not a log), never as a column on `customers` — found during Phase 6 that `customers_select_own` is row-level RLS, not column-level, so a `notes` column on `customers` would have been readable by the customer themself regardless of what the UI queried. Every `customer_notes` policy re-checks the target profile has `role = 'customer'`, so staff can't create a "note" against another staff/admin profile.
- `payments` has **no INSERT/UPDATE RLS policy for any role** (both dropped in Phase 7) — the only way a payment row is ever created is inside `place_order()`. Don't reintroduce `payments_insert_staff`/`payments_update_admin`; that would let any `sales_staff` insert an arbitrary payment row disconnected from a real order.
- Payment is simulated as instantly `'paid'` at order creation (no real gateway) — deliberate MVP simplification, not a bug.
- Order cancellation (pre-shipment only: `pending`/`confirmed`/`processing`, never after `shipped`) restores stock via a `'return'` movement but never directly touches `payments.status` at cancellation time — `orders.status = 'cancelled'` + `payments.status = 'paid'` together are the signal that a refund is outstanding. Phase 9 built the resolution path this was always reserved for: `sales_staff`/`admin` request `refund_payment`, super_admin approval flips **both** `payments.status = 'refunded'` and `orders.status = 'refunded'` atomically, and only for a payment whose order was cancelled through the approved `cancel_paid_order` flow specifically (re-checked at approval time via `exists (... action_type = 'cancel_paid_order' and status = 'approved')`, not just `orders.status = 'cancelled'` — a customer's own self-cancelled order does **not** qualify, deliberately, since that path bypasses the approval flow entirely). Don't add a second, looser way to reach `'refunded'` — this is the only sanctioned path.
- **Customer self-cancellation of their own `pending` order stays completely direct and unaffected by Phase 9** — only `sales_staff`/`admin` cancelling *any* order now requires approval (`update_order_status()` raises an explicit error for that combination). `super_admin` retains direct cancellation, consistent with their unrestricted power elsewhere (`profiles_update_super_admin`, `products_delete_super_admin`).
- `place_order()`/`update_order_status()` (both `SECURITY DEFINER`, `public` schema) follow the same hardening lessons learned from `customer_contact_email()`: `current_role()` captured into a typed local and checked for `NULL` explicitly (never relying on `NOT IN`'s null-handling), `anon`/`public` execute revoked and verified live via `has_function_privilege` (not just behavioral testing) before moving on. Apply both patterns to any future `SECURITY DEFINER` function in `public`.
- Cart is `localStorage`-only (`src/lib/cart.ts`) — no `cart_items` table. Deliberate exception to "no client-side state management": a persisted server-side cart would need a new table + RLS purely to hold pre-checkout, throwaway state.
- The 5 `dashboard_*` RPCs + `inventory_value_summary` view (Phase 8) are all `SECURITY INVOKER`, not `DEFINER` — none of them need privilege elevation, because RLS on the underlying tables (`orders`, `order_items`, `inventory_movements`, `profiles`, `inventory`) already scopes visibility correctly for every role, including the customer. A customer calling `dashboard_revenue_trend()` on `/account` gets only their own orders back (`orders_select_own`); staff calling the exact same function get store-wide data (`orders_select_staff`, unscoped) — no role branching inside any of these functions, no new RLS policies added. Verified live per-role, including that `inventory_staff` correctly gets an empty `dashboard_customer_growth()` result (no `profiles` visibility into customers, an existing Phase 3 restriction, not a Phase 8 regression).
- All 6 dashboard functions/views bucket dates using **Asia/Kolkata** (fixed UTC+5:30, no DST) via `at time zone 'Asia/Kolkata'`, even though every timestamp is stored in UTC — see `src/lib/dashboardRange.ts`. Every range is a **half-open interval** (`created_at >= p_from and created_at < p_to`), with `p_to` always the exclusive start of the day *after* the last included day, so the final selected day is never truncated. Both were verified against the exact boundary instant (an order placed at precisely IST midnight), not just approximately. Keep both conventions for any future date-bucketed function.
- **Critical lesson, applies project-wide, not just Phase 8:** `<script define:vars={...}>` combined with a static `import` statement is broken — Astro compiles `define:vars` scripts as inline, non-module tags, and `import` is a `SyntaxError` outside a module context. This was silently broken in four already-shipped files (see the bugfix commit above) since nobody had inspected actual compiled production output before Phase 8. The fix, and the pattern to use going forward: never use `define:vars` when the script also needs an `import` — instead serialize the server-rendered value onto a `data-*` attribute on an existing DOM element, and read it back from a plain `<script>` (no `define:vars`), which Astro/Vite properly extracts, bundles, and resolves imports for. `ChartCanvas.astro` is the reference implementation (also handles the case of a component rendered many times on one page, since Astro dedupes a component's script to run once regardless of how many instances exist).
- **Phase 9 approval requester access is action_type-specific, not role-flat**: `inventory_staff` → `delete_product` only; `sales_staff` → `cancel_paid_order`/`refund_payment` only; `admin` → all five action types; `super_admin` never requests, only reviews. Enforced twice — inside `create_approval_request()` (friendly error) and in `approval_requests_insert_own`'s `WITH CHECK` (the actual backstop) — so a raw REST insert can't grant a role more than its specific action types. Don't loosen either check independently of the other.
- `create_approval_request()` is `SECURITY INVOKER` (the insert it wraps is already RLS-permitted; no elevation needed) with full target/business-rule validation: action_type↔target_table mapping, target existence, duplicate-pending-request rejection, `delete_product` rejected if the product has *any* order_items or inventory_movements history, `deactivate_staff`/`change_role` rejected against a `super_admin` or `customer` target, `change_role`'s `new_role` restricted to an explicit allow-list (`sales_staff`/`inventory_staff`/`admin` only — never `super_admin`, never `customer`). `review_approval_request()` is `SECURITY DEFINER` (must reach `orders`/`payments`, which nobody has direct RLS write access to) and **re-validates every one of those same conditions again at approval time** before performing the side effect — state can change between request and review (verified live: an order that ships in the interim correctly fails a stale pending cancellation approval). Explicitly rejects reviewing your own request (`requested_by = auth.uid()`), even though today's role separation already makes that unreachable in the common case — defense-in-depth against an admin later promoted to super_admin approving their own old request.
- `approval_requests_update_super_admin` was **dropped, not replaced** — every status transition must go through `review_approval_request()`, so `status = 'approved'` can never be recorded without its paired side effect actually running (verified live: a raw `UPDATE approval_requests SET status = 'approved'` as super_admin now affects 0 rows). Same reasoning as `orders`/`order_items` having zero UPDATE policy since Phase 3 — don't reintroduce a raw table-write path for approval decisions.
- `products_write_staff` was split into `products_insert_staff`/`products_update_staff` (unchanged: `inventory_staff`/`admin`/`super_admin`) and `products_delete_super_admin` (new, super_admin only) — `inventory_staff`/`admin` lost direct DELETE capability entirely (verified live: 0 rows affected). Without this split, the approval gate on `delete_product` would have been optional — bypassable via a raw REST delete. `suppliers` deletion was deliberately **not** split the same way — stays fully direct/ungated, since suppliers carry no FK-restricted history the way products do (`inventory_movements.supplier_id` is `on delete set null`, not `restrict`).
- `inventory_adjustment` (the sixth `approval_action_type` value) stays **unreachable by design** — `record_inventory_movement()` is untouched by Phase 9, still direct for `inventory_staff`/`admin`/`super_admin`. Gating routine stock corrections behind super_admin review would break the real-time correction workflow Phase 5 was built for, for comparatively low/reversible risk.
